# UBCv2 跨数据集结果的可比性诊断

> 状态：**诊断完成（2026-11-15）；协议等价性已证（§6）；in-domain 训练已到 80K/120K（§6.6）**。
> 上游报告见 `UBCV2_GENERALIZATION.md`，本文只回答一个问题：
> **「GDROS 跨数据集 AEPE 22.0091 与论文 UBCv2 in-domain 4.49 差这么远、
> 而 M4 跨数据集只有 3.8941，这个对比该怎么读？」**

## 1. 为什么这个对比一开始就是错的

论文 UBCv2 行是**每档一个 (CMR, AEPE) 对**，不是单一 AEPE：

| | CMR@2 | AEPE@2 | CMR@3 | AEPE@3 | CMR@5 | AEPE@5 | AEPE | RMSE |
|---|---|---|---|---|---|---|---|---|
| 论文 GDROS（UBCv2 in-domain, w/ LSR） | 14.89(±0.38) | 1.56(±0.02) | 37.08(±0.04) | 2.13(±0.00) | 72.50(±0.42) | 2.97(±0.00) | 4.49(±0.00) | 11.97(±0.31) |

我们两行的训练域与测试集与它都不同：

| 单元格 | 训练域 | 测试集 | AEPE |
|---|---|---|---|
| 论文（上表） | UBCv2 | **作者筛后的 1447 对 × 3 seed** | 4.49 |
| 我们的 GDROS `GDROS-os512.pth` | **OS** | 本地生成的 1625 对 × 1 seed | 22.0091 |
| 我们的 E075A-M4@80K | **OS** | 同一批 1625 对 | 3.8941 |

唯一能直接相减的是后两行。（同集合、同 LSR、同 `iters=32`）。

### 1.1 把三行按论文列序摆开，立刻看出差别在「覆盖」不在「精度」

| 对象 | 训练域 | CMR@2 | AEPE@2 | CMR@3 | AEPE@3 | CMR@5 | AEPE@5 | AEPE |
|---|---|---|---|---|---|---|---|---|
| GDROS（OS 训） | cross | 0.74 | **1.46** | 2.83 | **2.24** | 11.26 | **3.61** | 22.01 |
| M4@80K（OS 训） | cross | **62.95** | **0.71** | **68.68** | **0.85** | **74.52** | **1.10** | **3.89** |
| 论文 GDROS | in-domain | 14.89 | 1.56 | 37.08 | 2.13 | 72.50 | 2.97 | 4.49 |

两点值得注意：

- **GDROS 跨域后的「成功对」精度几乎没退**：`AEPE@2/3/5 = 1.46 / 2.24 / 3.61`，
  与论文 in-domain 的 `1.56 / 2.13 / 2.97` 基本同档。它坏的是**覆盖率**
  （`CMR@2` 从 14.89% 掉到 0.74%），不是命中后的准度。
  ⇒ 「换域失效」的正确表述是「大部分对根本对不上」，不是「对上了也不准」。
- **M4 的分布在 2px 处密集得多**：`CMR@2 62.95` 而 `CMR@5 74.52`，
  即只有 11.6% 的对落在 [2,5) px；论文 in-domain 有 57.6% 落在 [2,5) px。
  M4 的「成功对」均值 `AEPE@5 = 1.10` 也比论文的 `2.97` 小 2.7 倍。

`RMSE` 口径：官方 `test.py` 打印在 RMSE 栏位的是 `np.var(MAE_list)`（方差），
但论文 `11.97 / 4.49 = 2.67` 的量级更像**标准差**。我们两行的三种候选：

| 对象 | var（官方栏位） | std = sqrt(var) | 逐像素 RMSE | std/AEPE |
|---|---|---|---|---|
| GDROS（OS 训） | 679.05 | 26.06 | 39.21 | 1.18 |
| M4@80K | 38.76 | 6.23 | 8.75 | 1.60 |
| 论文（若 11.97 就是 std） | 143.28 | 11.97 | - | 2.67 |

⇒ 对标 `11.97` 时要用 std，不能直接拿方差栏位去比。

## 2. 先排除一种可能的解释：论文筛掉了病态对？

论文三个 split 的筛选率高度一致：

| split | 原始 | 论文 | 保留率 |
|---|---|---|---|
| train | 4008 | 3517 | 87.7% |
| val | 1681 | 1437 | 85.5% |
| test | 1625 | 1447 | 89.0% |

看起来像「统一剔掉约 11–14% 的劣质对」。如果被剔的正好是 GDROS 完全失败的那些对，
CMR@2 从 0.74% 掉到论文的 14.89% 就说得通了。

**用官方口径的阈值分档直接反解，可以否定这个解释。**
GDROS 的 `@5px` 档给出：`CMR=11.2615%`（183 对）、`AEPE@5=3.6080`。于是

- 183 对良好对，贡献 `3.6080 × 183 = 660.3`
- 总 AEPE 和 `22.0091 × 1625 = 35764.7`
- 剩下 1442 对（失败对）均值 `(35764.7 − 660.3) / 1442 = 24.34 px`

若只靠筛对把总 AEPE 压到 4.49，需要保留 `35764.7 / 4.49 = 7965` 对 —— 比现有
1625 对还多，**结构上不可能**。即使只留下那 183 对良好对，AEPE 也只到 3.61，
而论文是 4.49（且论文保留了 89%）。

⇒ **筛选率不能解释这个差距。** 差距只能来自训练域（或预处理）。

## 3. 逐对诊断：GDROS 的失败与几何难度无关

`diag_ubcv2_pairs.py` 对 1625 对逐对记录误差，并用 `datum/<id>.json` 里已知的
`M` 重算 warp 后的**有效重叠区**（`warpAffine(ones, M)`）：

| 指标 | 值 |
|---|---|
| `AEPE_full`（全图，即发布口径） | 22.0091 |
| `AEPE_overlap`（只算真实有源像素的区域） | **21.8421** |
| `CMR@5 full` / `overlap` | 11.26% / 11.51% |
| 有效重叠区占比 | 均值 0.884，p10 0.770 |
| `corr(EPE, overlap)` | **0.029** |
| `corr(EPE, |rotation|)` | **−0.041** |
| `corr(EPE, |scale−1|)` | **0.037** |

分桶也只是平的：

| 桶 | 对数 | AEPE | CMR@5 |
|---|---|---|---|
| \|rot\| ∈ [0°,3°) | 375 | 23.54 | 10.40% |
| \|rot\| ∈ [9°,10°] | 327 | 21.20 | 11.93% |
| overlap ∈ [0.60,0.75) | 91 | 20.03 | 16.48% |
| overlap ∈ [0.85,1.0] | 1113 | 22.15 | 9.25% |

**旋转更大不更难，重叠更少也不更难，扣掉无信息边框只回收 0.17 px。**
所以这不是「仿射幅度设得比论文激进」的问题，也不是边框黑区问题。

再看 GDROS 预测流的最小二乘仿射：`pred_scale` 中位数 **0.9958**、
`pred_rot` 均值 **0.082°** ⇒ 预测出来基本是**恒等变换**，即「没有配准」。

## 4. 用「零流基线」把绝对数放到同一把尺子上

因为 `truth_flow` 是解析的，可以直接算出「预测零流」时官方口径的 AEPE。
在本地这套实现（绕原点旋转，见 `build_ubcv2_testset.py` 的约定）下：

| 对象 | AEPE | 相对零流基线的增益 |
|---|---|---|
| 零流恒等基线 | 29.7910 | — |
| GDROS `GDROS-os512.pth`（OS 训练） | 22.0091 | **26.1%** |
| E075A-M4@80K（OS 训练） | 3.8941 | **86.9%** |
| 论文 GDROS（UBCv2 in-domain） | 4.49 | 84.9% |

读法：**GDROS 换到 UBCv2 后几乎不工作**（只比什么都不做强 26%），
而 M4 把误差压掉了 87%。论文 in-domain 的 4.49 按同一把尺子是 85% ——
与 M4 跨数据集的档次相当，而不是 M4 反超。

⚠️ 最后一行只是量级参照，不是同集合比较：`4.49` 是在作者的 1447 对 × 3 seed 上
得到的。

## 5. 绝对数不可跨实现比较：旋转中心是 1.83 倍的自由度

论文只说 translation ±15 px、scale 0.9–1.1、rotation ±10°，**没说旋转/缩放的基准点**。
我们沿用官方 OS `datum/*.npy[2]` 的形式（绕原点），若换成 `cv2.getRotationMatrix2D`
那种绕图像中心的写法，同样的参数下零流基线是：

| 实现 | 零流基线 AEPE |
|---|---|
| 绕原点（当前，与官方 OS `datum` 一致） | 29.7910 |
| 绕图像中心 | 16.3021（**1.83× 更容易**） |

⇒ 任何**绝对 AEPE/CMR 都不能与论文 Table III/V 并列**，只能做同集合内的横向对比。
这一点已在 `UBCV2_GENERALIZATION.md` 的边界里写明，本文给出定量幅度。

## 6. 协议等价性：与「能不能复现论文数值」是两件事

这是本文最需要说清的一节。担心是「复现不了论文数值 ⇒ 说明评测口径不同」，
但这个推理不成立：**口径是否相同可以单独证明，且已经证明了。**

### 6.1 证据一：指标实现逐行同构

官方 `test.py` 的核心只有四行：

```python
epe = torch.sum((flow_pre - flow_gt)**2, dim=0).sqrt()   # 逐分量 |Δx|,|Δy|
epe_list.append(epe.view(-1).numpy())
epe_ = np.mean(epe.view(-1).numpy()); MAE_list.append(epe_)
MAE_1, RMSE_1, CMR_1 = Registration_index_calculation(MAE_list, 1)
```

`Registration_index_calculation` 里 `MAE = np.mean(MAE_list)`、
`RMSE = np.var(MAE_list)`、`CMR = mean(MAE_list < T)`。
我们的 `eval_ubcv2_official_protocol.py` 与 `_official_protocol.py` 用的是同一套
结构（逐分量 L2 → 配对均值 → 配对级聚合），**没有一处不同的聚合层级**。
⇒ 两者不是「相似」，是同一个口径的两种实现。

### 6.2 证据二：在**我们的**数据集上，官方 `test.py` 跑出逐位相同的数

用官方 `test.py`（`iters=32`、`LSR Npoint` 默认 200000、`image_size=[512,512]`、
released `GDROS-os512.pth`）直接跑我们生成的 UBCv2 seed901 测试集：

| 指标 | 官方 `test.py` | 我们的 harness JSON | Δ |
|---|---|---|---|
| AEPE | `22.009050` | `22.009050187680995` | 0 |
| RMSE（官方差栏） | `679.046204` | `679.0461798222686` | ~2e-5 |
| CMR@1..5 | `0.06 / 0.74 / 2.83 / 6.83 / 11.26%` | 同 | 0 |
| MAE@1..5 | `0.7631 / 1.4557 / 2.2354 / 2.9918 / 3.6080` | 同 | 0 |

⇒ **同一份数据、同一个权重、两套独立代码，输出逐位相同。** 这一条比任何论文数值都强，
因为它证明的是「我们的评测器 = 官方评测器」，而不是「我们的训练 ≈ 论文的训练」。

### 6.3 证据三：官方数据集上，官方 `test.py` 复现出历史基准

官方 OS 424 对、released 权重：`test.py` 输出 `EPE 1.461846 / RMSE 0.746347`、
`CMR@1..5 = 33.73 / 81.60 / 92.69 / 98.11 / 99.53%`、
`MAE@1..5 = 0.7420 / 1.1249 / 1.2820 / 1.3994 / 1.4431`。
与我们历史上报的 OS 基准 `1.4618` 与 `CMR 33.73 / 81.60 / 99.53` **完全吻合**。

这条证明的是「我们的 harness 在别人的数据上也没有偏移」—— 一条在自家数据上的
一致性可能只是共同 bug，两条合起来才能排除。

### 6.5 那为什么论文的 UBCv2 行本来就难以逐位复现

三条**独立**的、与口径无关的障碍：

1. **官方从未发布 UBCv2 权重。** README 只说 *"models trained on WHU-OPT-SAR dataset
   and OS dataset respectively"*；GitHub Releases 页为空（*"There aren't any releases
   here"*）；数据下载只给 WHU-OPT-SAR 与 OS，不给 UBCv2 筛后 split。
   ⇒ 论文的 UBCv2 行**没有可用的公开权重去直接验证**，这不是我们训练的问题。
2. **论文的预筛算法未公开。** 原文只说 *"we remove such data by a pre-screening step,
   and finally reach a split of (3,517 / 1,437 / 1,447)"*，没给判据、没给阈值。
   我们只能拿到 4008 / 1681 / 1625 的原始切分。§2 已证明这个筛选率**不足以**
   解释 22.0 → 4.49 的差距，但它仍然是一个未知的自由度。
3. **论文正文与发布代码的超参不一致。** 论文 Section III-C/IV-B 写
   *"AdamW … initial learning rate of **1.2e-5**, a **batch size of 12**,
   and a maximum iteration of 120,000 steps"*；而 `configs/default.py` 是
   `batch_size=2`、`canonical_lr=12.5e-5`，且 `core/optimizer/__init__.py` 里
   `lr = config.canonical_lr` **直传、不按 batch size 缩放**。两者相比：

   | | 论文正文 | 发布代码 | 比值 |
   |---|---|---|---|
   | batch size | 12 | 2 | 6× |
   | 总样本量（×120K） | 1.44 M | 240 K | **6×** |
   | LR 峰值 | 1.2e-5 | 1.25e-4 | **10.4×** |

   LR 高 10× 而每步样本少 6×，训练动力学完全不同。我们照**代码**跑，这是唯一
   可辩护的可复现基线（代码是实际产生论文数字的那份实现，正文大概率是笔误）。

**结论**：口径一致 = 已证（§6.1–6.3，三重、跨数据、逐位）；
论文数值能否逐位复现 = 受上面三条限制，**不能作为口径是否一致的前提**。
换句话说，即使 in-domain 训练最终只跑到 AEPE 8 而不是 4.49，也只说明
「我们的集合/预处理与作者不同」，不说明「我们测的东西不一样」。

### 6.6 in-domain 训练的读法（判据先定好）

官方代码 recipe（`bs=2`、`canonical_lr=1.25e-4`、`iters=12`、120K 步）在
4008 对 UBCv2 train split 上训练，每 20K 存一个 checkpoint，在**同一批 1625 对**
（seed901）上按官方口径评测：

| step | AEPE | CMR@2 | CMR@3 | CMR@5 | AEPE@5 | 逐像素 1px | RMSE(std) |
|---|---|---|---|---|---|---|---|
| 20000 | 10.6216 | 0.00 | 0.80 | 7.75 | 3.994 | 6.47 | 5.130 |
| 40000 | 8.5199 | 0.06 | 0.62 | 13.85 | 4.178 | 7.98 | 4.058 |
| 60000 | 8.6503 | 0.12 | 2.58 | 21.23 | 4.032 | 8.29 | 5.017 |
| 80000 | **8.2769** | **0.00** | 0.86 | **17.85** | 4.209 | 8.29 | 4.300 |
| 论文 | **4.49** | **14.89** | 37.08 | **72.50** | 2.97 | - | 11.97 |

**40K 之后就基本平了**（AEPE 8.28–8.65，CMR@5 在 18–21% 之间振荡），
`CMR@2` 从 0.00 到 0.12% 之间乱跳。相对跨域（`AEPE 22.01 / CMR@5 11.26`）确实有
大幅改善（AEPE 2.7×、CMR@5 +7~10 pt），但**离论文的 `CMR@2 14.89 / CMR@5 72.50`
差得不是一点**：`CMR@2` 差两个数量级。

再看训练日志（`core/loss.py` 的指标，**注意训练侧不算 LSR**）：

| | 逐像素 1px | 3px | 5px | epe |
|---|---|---|---|---|
| WHU 官方 recipe @120K | 27.97% | 83.08% | **93.70%** | 低 |
| 我们 UBCv2 @10K | 0.16% | 1.48% | 3.96% | 33.81 |
| 我们 UBCv2 @80K | 0.44% | 3.87% | **9.21%** | 21.15 |

⇒ **GDROS 连自己的训练集都拟合不了**（5px 内像素占比 9.2% vs WHU 的 93.7%，差 10×）。
这不是「测试集更难」，而是「这套前端在 UBCv2 的表观域里根本学不动」。
把它与论文 Table III 并列是站不住的。

**但有一个仍然成立的强结论**：同一批 1625 对、同一口径、同一 LSR，

| 对象 | 训练域 | AEPE |
|---|---|---|
| M4@80K | OS | **3.8941** |
| GDROS | **UBCv2（in-domain）** | 8.28–8.65 |
| GDROS | OS（cross） | 22.0091 |

**M4 用 OS 权重、跨域，仍然比在 UBCv2 上亲自训过的 GDROS 好 2.1–2.2×。**
这个比较不需要论文数值，也不需要假设我们的集合与作者同档 —— 两个数在同一张表里。

⚠️ 反过来的推论要小心：不能说「我们的集合比论文难」当结论，因为真正的差异更可能
在 **SAR 预处理**（我们用的是全图固定 p2/p98 对数 LUT，作者用什么没公开）。
若要闭合，需要试「按图归一化 / dB clip」等几种 SAR 强度映射，看 5px 覆盖率能否抬起来。
这也是为什么把论文的 `4.49` 当复现目标要谨慎：复现对象里含一个未知的预处理自由度。

## 7. 由此确定的下一步：在 UBCv2 上训 GDROS

既然(a) 筛选解释被排除，(b) 几何难度无关，(c) 预测退化为恒等，
那么 22.0091 只能是**外观域差异**（SAR 辐射、纹理）导致前端失效。
唯一能把它拆开的手段就是**在 UBCv2 上按官方 recipe 训练 GDROS**，再在同一批
1625 对上评测。

**结果（§6.6）已出，两条预判都不成立**：GDROS 训到 80K 只回到 AEPE 8.28
（不是 4–5，也不是 15+），且训练集自身 5px 覆盖率只有 9.2%。所以「域差异导致
前端失效」这个判断是对的，但比预期更严重 —— **换域训练也没能修好它**，
说明瓶颈不在「用哪套权重」，而在「GDROS 这类 RAFT 式相关体前端 + 这张 SAR 图」
这个组合本身。M4 换域不训就有 3.89，把这一点的价值放大了。

**仍未闭合的一格**：GDROS 是「UBCv2 训练 vs UBCv2 测试」，
而 M4 是「OS 训练 vs UBCv2 测试」。要得到严格同条件的表，还需要在 UBCv2 上重训
M4 整链（≈16.5 h）。届时才有四个格子：

| | OS 训练 | UBCv2 训练 |
|---|---|---|
| GDROS | 22.0091 | **8.2769**（@80K） |
| M4 | 3.8941 | ← 待补 |
