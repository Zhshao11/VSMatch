## 1. 目的与边界

使用作者发布的完整 `testing.zip` 和 `GDROS-os512.pth`，验证当前评测入口能否在 424 对
OS 数据上复现论文量级结果。E-000 不改变网络 forward、相关体、GRU、LSR 或 checkpoint，
只允许数据路径校验、指标记录和结果持久化。

重新生成的 OS 数据和从不完整归档推导出的协议只能作为 diagnostic，不能替代本实验。

## 4. 执行步骤

1. 审计远端 git diff、数据目录、checkpoint、Python/CUDA 和 watchdog 状态。
2. 校验本地归档并记录哈希。
3. 使用支持 partial 和校验的传输方式上传到独立 staging 文件。
4. 校验远端 staging 的字节数、SHA256 和 ZIP 完整性。
5. 保留旧坏文件备份，将已验证 staging 原子重命名为正式归档。
6. 解压到新的 `gdros_official_e000_archive` 目录，不覆盖现有
   `gdros_official` 或 `gdros_official_reconstructed`。
7. 校验三类数据的数量、命名、尺寸，并与归档清单对应。
   发布前和原子重命名后各执行一次完整校验；最终 provenance 必须绑定现存发布目录、
   官方 ZIP SHA/size/CRC、2120 个数据文件和 424 对。
8. 独立子 agent 审阅当前评测 diff 和调用路径；修复高风险问题后复核。
9. 运行 1 对样本 smoke test，与现有参考 per-pair EPE 比较。
10. 通过 watchdog 在空闲单卡上运行完整 424 对评测。
11. 汇总指标、P95/P99、失败率、日志、命令、GPU 和代码状态；同步到本地结果目录。

## 6. 通过条件

1. 官方归档和远端正式归档 SHA256 完全一致。
2. 数据三元组为 424 对，无缺失、错序或 stem 不一致。
3. checkpoint 严格加载，无 missing 或 unexpected keys。
4. smoke test 与完整评测均完成，无静默跳过样本。
5. AEPE 与论文/发布 checkpoint 的已知结果处于可解释误差范围，并报告 CMR@1/2/5。
6. 独立代码审阅确认 E-000 没有改变 baseline 算法行为。

指标命名必须同时保留数学上的 pair-EPE 标准差和公开代码方差。论文所谓 RMSE 约 `0.75`
实际对应 `np.var(pair_epe)`，不能把数学标准差字段无解释地命名为论文 RMSE。

只有 E-000 通过后，`E-001` 才能从 `DRAFT` 转为 `READY`。
